# 公网多人猜数字游戏设计规格

## 1. 目标

将现有的单文件猜数字页面逐步迁移为可部署到公网的多人联机应用。第一阶段迁移并稳定单机玩法和现有视觉体验；后续阶段增加安全账号体系、好友关系、实时 1v1 PK、在线排行榜和断线恢复。

原始附件 `guess-number-game-8.html` 保持不变。新项目位于 `D:\项目\guess-number-online`，所有实现、测试和部署配置均在新项目中维护。

## 2. 设计原则

- 服务端权威：秘密数字、猜测次数、对局状态、胜负和积分只由服务端判定。
- 渐进迁移：每个阶段都能独立运行和验收，不进行一次性大重写。
- 明确信任边界：客户端输入、用户资料、网络响应和持久化数据均视为不可信。
- 可恢复：实时连接中断后能够恢复账号会话和正在进行的对局。
- 可测试：核心游戏规则与浏览器、网络和数据库解耦。
- 控制复杂度：单实例阶段不引入 Redis；只有多实例部署确有需要时才增加。

## 3. 技术架构

采用 TypeScript 单仓库结构：

```text
guess-number-online/
  apps/
    web/       React + Vite 前端
    server/    Fastify + Socket.IO 服务端
  packages/
    game-core/ 纯游戏规则与共享类型
  docs/
  docker-compose.yml
  package.json
```

前端使用 React、TypeScript 和 Vite，迁移当前页面的主题、布局和反馈交互。服务端使用 Fastify 提供 HTTP API，Socket.IO 提供在线状态、邀请和 PK 实时事件。PostgreSQL 保存账号、会话、好友关系、对局、猜测记录和积分流水。

生产环境中前端和 API 使用同一站点来源。会话使用安全 Cookie，因此浏览器代码不读取或持久化访问令牌。

## 4. 分阶段范围

### 阶段一：单机迁移与工程基础

- 建立 TypeScript 单仓库、代码质量和测试工具。
- 提取无浏览器依赖的 `game-core`。
- 迁移当前主游戏界面、五套主题、输入校验、提示、机会点和结果面板。
- 保留游客、本地主题和本地战绩。
- 移除本地密码注册和登录；本地身份只作为游客档案，不宣称提供安全认证。
- 消除动态数据的 `innerHTML` 拼接。
- 提供响应式布局、键盘操作、减少动画支持和可访问弹窗基础设施。

### 阶段二：账号与持久化

- 增加 PostgreSQL 数据模型和迁移。
- 实现注册、登录、注销、当前用户、历史战绩和排行榜 API。
- 密码使用 Argon2id 哈希。
- 使用服务端会话和 `HttpOnly + Secure + SameSite=Lax` Cookie。
- 增加输入验证、登录与注册限流、统一错误响应和审计日志。

### 阶段三：好友与实时 PK

- 增加在线状态、好友申请、好友列表和 PK 邀请。
- 服务端创建对局和秘密数字，客户端不接收答案。
- 客户端每次只提交一个猜测，服务端返回大、小或正确。
- 服务端通过事务和状态检查原子结算胜负、积分及战绩。
- 增加断线重连、快照恢复、对手离线宽限期和超时结算。

### 阶段四：公网部署加固

- 提供生产 Docker 镜像、反向代理、HTTPS、健康检查和结构化日志。
- 配置备份、数据库迁移流程、监控和告警。
- 根据实际并发数据决定是否增加 Redis 和横向扩容。

## 5. 核心组件

### `packages/game-core`

负责数字范围、最大次数、猜测校验、重复猜测、区间收窄和终局判定。它不访问 DOM、网络、存储或随机数全局对象；秘密数字由调用方传入，从而保证测试确定性。

核心状态至少包含：

- `secretNumber`
- `minNumber` 与 `maxNumber`
- `attemptLimit`
- `attempts`
- `guesses`
- `lowerBound` 与 `upperBound`
- `status: ready | active | won | lost`

### `apps/web`

负责页面渲染、表单交互、主题、本地游客战绩和与服务端通信。界面状态与游戏规则分离；组件不得自行判断联机胜负或修改在线积分。

第一阶段主要组件包括 `GamePage`、`GuessForm`、`GameFeedback`、`GameStats`、`GuessHistory`、`ResultPanel`、`ThemePicker` 和可访问的 `Dialog`。

### `apps/server`

负责身份认证、权限、用户资料、好友、在线状态、对局状态机、猜测判定和积分结算。所有改变积分或对局结果的操作都必须经过已认证用户、房间成员校验和数据库状态校验。

## 6. PK 状态机与数据流

服务端对局状态为：

```text
pending -> active -> finished
                  -> cancelled
                  -> expired
```

流程如下：

1. 挑战方创建邀请，服务端生成 `pending` 邀请。
2. 对方接受后，服务端创建 `active` 对局并生成秘密数字。
3. 双方客户端收到不含秘密数字的房间快照。
4. 玩家提交 `guess`；服务端校验成员身份、对局状态、整数范围、重复值和次数限制。
5. 服务端返回该玩家的 `low`、`high`、`correct` 或 `lost` 结果，并广播安全的房间进度。
6. 首位正确猜中的玩家触发原子结算；并发请求中只有一次状态转换可以成功。
7. 服务端保存对局、双方猜测记录和积分流水，然后向双方广播 `finished` 快照。

每个改变状态的客户端命令都携带唯一事件 ID。服务端记录或识别重复事件，确保重连和重试不会重复猜测或重复加分。

## 7. 断线与异常处理

- Socket.IO 自动重连期间，前端显示“正在重连”，但保留最后一次可信快照。
- 重连成功后，客户端请求当前房间快照，而不是重放本地推测状态。
- 对手断线后进入可配置宽限期；超时结果由服务端统一判定。
- 数据库不可用或对局服务异常时拒绝创建新对局，不写入不完整战绩。
- HTTP 和实时事件返回稳定错误码；前端显示面向用户的中文信息。
- 服务器内部错误、堆栈和数据库细节只写入服务端日志，不返回浏览器。

## 8. 安全要求

- 生产环境只允许 HTTPS/WSS。
- 密码使用 Argon2id 独立加盐哈希，不记录明文密码。
- 会话标识只存放在安全 Cookie 中，不进入 URL、`localStorage` 或普通 JavaScript 状态。
- 所有用户或服务器提供的文本使用 React 文本渲染或 `textContent`，不拼接动态 HTML。
- HTTP 请求与 Socket 事件均进行运行时数据校验。
- 注册、登录、加好友、创建邀请和提交猜测分别限流。
- 服务端忽略客户端提交的胜负、积分增量、剩余次数和答案。
- 数据库为用户名规范化值设置唯一约束；好友关系、邀请和结算使用唯一约束或事务防止重复。
- Cookie 会话配合严格来源检查；跨站部署时再增加显式 CSRF 令牌。

## 9. 初始数据模型

- `users`：用户 ID、规范化用户名、展示名、密码哈希、积分、创建时间。
- `sessions`：会话 ID、用户 ID、过期时间、撤销时间和安全元数据。
- `friendships`：双方用户 ID、状态和时间戳。
- `challenges`：挑战双方、状态、过期时间和关联对局。
- `matches`：双方用户、状态、秘密数字、赢家、开始与结束时间、版本号。
- `match_players`：对局用户、已用次数、完成状态和断线时间。
- `guesses`：对局、用户、顺序、猜测值、结果和事件 ID。
- `score_events`：用户、积分变化、原因、关联对局和唯一幂等键。

秘密数字可以存入数据库，但任何面向客户端的查询和序列化类型都不得包含该字段。

## 10. 测试策略

### 阶段一

- `game-core` 单元测试覆盖最小值、最大值、非整数、越界、重复猜测、区间收窄、猜中和机会耗尽。
- 前端组件测试覆盖提交、错误提示、重开、主题切换、结果展示和键盘操作。
- 构建测试确保 TypeScript 类型检查和生产打包通过。
- 浏览器冒烟测试验证桌面与窄屏主要流程。

### 后续阶段

- API 集成测试覆盖注册、登录、注销、越权、过期会话和限流。
- 数据库测试覆盖唯一约束、事务回滚和积分幂等。
- Socket 集成测试覆盖邀请、双方猜测、并发猜中、重复事件、断线恢复和超时。
- 安全回归测试覆盖动态文本注入、令牌泄漏和客户端伪造积分或结果。

## 11. 第一阶段验收标准

- 新项目可通过文档中的单一命令安装和启动。
- 当前猜数字主流程、五套主题和移动端布局完成迁移。
- 游戏引擎不依赖 DOM，且核心边界测试全部通过。
- 页面不包含本地密码认证、联机令牌查询参数或客户端积分上报代码。
- 动态用户名、反馈和错误信息不通过 `innerHTML` 渲染。
- 类型检查、单元测试、生产构建和浏览器冒烟检查均通过。
- 原始附件未被修改。

## 12. 本阶段不做的事项

- 第一阶段不实现真实注册、好友、匹配或在线 PK。
- 第一阶段不引入 PostgreSQL、Redis 或云服务账号。
- 不加入聊天、付费、皮肤商城、赛季系统或复杂反作弊。
- 不在没有容量数据的情况下设计多区域和多实例架构。
